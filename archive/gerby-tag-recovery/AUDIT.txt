ROOT CAUSES

1. Docker builds run make gerby-deploy-build
      from an old checked-in registry. Each
   image
   independently allocates IDs for new labels
   in source order. No resulting registry is
   fed back into Git. Adding or moving source
   labels therefore shifts later assignments
   between independent deployments.

2. The old tagger reads an inactive row's ID
   but discards its label and fails to emit
   that row. After another build, the ID can
   leave the high-water mark and be reused.
   Reintroduced labels also lose their IDs.

3. Earlier checked-in registries themselves
   were replaced or truncated. For example,
   fd009140a contains only 26 rows; the June
      11 revision restarts at 0000. The
   September
   24 regeneration b558d2deb has thousands
   of changes. Historical conflicts predate
   the three currently reported links.

4. Fresh SQLite databases contain no old
   identities to reject reassignment. The
   importer overwrote labels when reusing a
   tag and only logged later discrepancies.

5. The web view guessed replacements using
      printed numbers/types and guessed
   chapters.
      Those guesses could change a URL's
   meaning.

6. Duplicate source labels were silently
   given occurrence-based '-duplicate-N'
   suffixes. Reordering duplicates could
   change identities. The recovered registry
   contains 52 labels with those suffixes.
   New conversion now fails on duplicates;
   explicit source labels need editorial
   reconciliation before a complete build.

IMPLEMENTED SAFEGUARDS

registry/tags is reviewed source data outside
the generated gerby directory. The old
tracked
gerby/tags is removed from Git tracking;
local
render output remains ignored. Builds derive
an active/tombstone view from the source
file.

Every build checks all checksummed registry
snapshots. Conflicting assignments, missing
IDs, changed identities, invalid rows,
duplicate IDs/labels, migration cycles,
missing evidence and changed evidence fail
before registry output or database mutation.

New tags require an explicit local allocation
step, make gerby-register, followed by review
and commit. Allocation holds an OS file lock,
writes atomically and starts above ALL IDs
in the validated registry. Four-character
space exhaustion fails without partial
output.
Normal builds never allocate new IDs.

Git history checks compare the candidate with
the PR base and prohibit
deletion/reassignment
of previously committed mappings or
alteration
of old evidence. Required CI and review must
be configured before deployment. Checksummed
files are an integrity check, not protection
against someone deliberately changing code
and its checks together.

Import checks validate rendered tag
identities
and any existing database before any writes.
WSGI startup validates registry history,
rendered output and active database
membership.
This also covers Railway's start-command
configuration override.

Retired tags return HTTP 410. Unknown or
unrendered tags return HTTP 404. Neither path
guesses another mathematical referent.
A tombstone reserves an identity; it does not
reconstruct deleted mathematical content.

No code can infer whether an author reused a
label for a different mathematical statement.
Source-label reuse and explicit migrations
still require mathematical/editorial review.
