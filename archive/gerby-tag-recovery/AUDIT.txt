ROOT CAUSES

1. Docker builds run make gerby-deploy-build
      from an old checked-in registry. Each
   image
   independently allocates IDs for new labels
   in source order. No resulting registry is
   fed back into Git. Adding or moving source
   labels therefore shifts later assignments
   between independent deployments.

2. The old tagger reads an inactive row's ID
   but discards its label and fails to emit
   that row. After another build, the ID can
   leave the high-water mark and be reused.
   Reintroduced labels also lose their IDs.

3. Earlier checked-in registries themselves
   were replaced or truncated. For example,
   fd009140a contains only 26 rows; the June
      11 revision restarts at 0000. The
   September
   24 regeneration b558d2deb has thousands
   of changes. Historical conflicts predate
   the three currently reported links.

4. Fresh SQLite databases contain no old
   identities to reject reassignment. The
   importer overwrote labels when reusing a
   tag and only logged later discrepancies.

5. The web view guessed replacements using
      printed numbers/types and guessed
   chapters.
      Those guesses could change a URL's
   meaning.

6. Duplicate source labels were silently
   given occurrence-based '-duplicate-N'
   suffixes. Reordering duplicates could
   change identities. The recovered registry
   contains 52 labels with those suffixes.
   New conversion now fails on duplicates;
   explicit source labels need editorial
   reconciliation before a complete build.

PERMANENT IDENTITY POLICY

Evidence has three kinds, all checksummed
in registry/history.json (format 2).

* Canonical: the 2026-10-16 production
  registry, and the repair baseline (that
  file plus the 350 tombstones of the last
  checked-in registry). Every assignment
  in them is permanent.
* Allocation: registry/snapshots/<sha>.tags,
  one file per explicit allocation. It
  holds only the new rows and is named by
  its SHA-256.
* Legacy: the 15 old checked-in
  registries, plus the 111 reconstructed
  build observations. They may contradict
  each other. They serve only as
  reservations and as public provenance.

Invariants. Every build, import and WSGI
startup checks the first five, and fails
closed if any is violated.

I1 registry/tags is well formed: valid IDs,
   no duplicate tag, no duplicate label
   after migrations.
I2 Every evidence file matches its
   checksum, and at least one canonical
   snapshot exists.
I3 The tag-to-label map of registry/tags
   EQUALS the union of the canonical and
   allocation snapshots. Nothing is lost,
   reassigned or unrecorded. Two snapshots
   that disagree fail ("Conflicting
   canonical tag"). This is also how
   concurrent branches that allocated the
   same ID are caught.
I4 An allocated ID is at least the floor
   0G00 and was never observed in legacy
   evidence. The one exception is
   recovering the single legacy meaning of
   that same label.
I5 The rendered registry is exactly the
   committed registry, with active flags
   taken from the source. Builds never
   allocate.
I6 In Git, history is append-only: base
   snapshots, roles, allocation files and
   mappings cannot be removed or changed,
   and the floor cannot drop. GitHub
   checks this on pull requests and pushes.

Allocation floor. Every old build
allocated sequentially above the maximum
of its checked-in registry, one ID per
unregistered label. Over all 653
recoverable deployment commits, that
maximum plus every \label and file count
is at most 0EMB (16,909). The one
unrecoverable commit is a FAILED build.
Current main gives the same bound. 0G00
(18,496) leaves about 1,600 IDs of margin.
So no new tag can collide with an ID that
any past or interim old-allocator build
could have served, even an unrecovered
one.

Tag classes and HTTP behavior:

  active, rendered       200 page
  active, no page        404, explains
                         (09DP)
  retired tombstone      410
  historical, 1 label    410, label shown
  ambiguous, 2+ labels   410, all shown
  reserved, below 0G00   404, reserved
  unknown or invalid     404

Nothing redirects. /tag/<tag>/provenance
lists every recorded label with its
sources. Where such a label still exists,
it shows that label's CURRENT tag as a
plain link. An active tag with
contradictory history serves its current
referent and shows a notice linking to its
provenance.

IMPLEMENTED SAFEGUARDS

New tags exist only after make
gerby-register, which takes a file lock.
It writes the allocation delta durably
BEFORE replacing registry/tags. If it is
interrupted, the next check fails ("Lost
historical tag"). Rerunning make
gerby-register restores the reserved rows.
Docker and make gerby-import only render.

Duplicate source labels. The converter
refuses them. The 52 occurrences that
production had numbered '-duplicate-N'
by position are now explicit in the
source. Only the \label argument changed.
gerby/book.tex is byte-identical to the
legacy converter's output, except for one
label lowercased for AGENTS.md. A
migration keeps that label's tag, 05FZ.
No \ref pointed to any of these labels,
so PDFs are unaffected.

Rendering. plasTeX's fancyvrb called
strip() on macro values such as
\footnotesize. scripts/plastex_gerby.py
now passes their macro names instead. This
fixes the current Railway failure without
editing homological-algebra.tex, and
supersedes PR #11.

PR #11 alone is unsafe. Running the
archived production allocator on current
main reassigns 275 live tags, including
09DN, 09DP and 09DR.

Changes on main since production. Main
deleted or relabeled four rendered items
after commit f968b17dd: 09AJ (section
removed in acc0b9b1c), 09AT, 09AU and
09AV. In faa301d16, the paraphrased Cech
subsections were replaced by
transcriptions under new labels
subsection-jethro-cech-N. Under the
label rule these retire (HTTP 410) and
the new labels get new tags. Whether a
migration should keep 09AT-09AV is an
editorial decision for the author. The
decision must be made before the merge.
06X3 also retires: its \label is
commented out, and it never had a page.

09DP. Its label is attached to bold
run-in text, not to an environment or a
sectioning command. Gerby therefore has
no node to tag. It has never had a page.
Wrapping the text in an environment
would make 09DP render under the same
ID. That is an editorial change.

No code can tell whether an author reused
a label for a different mathematical
statement. Migrations need editorial
review.
